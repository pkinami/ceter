codex exec "# Ceter Technology Website Rebuild

Rebuild the existing website from the ground up as a modern e-commerce platform for Ceter Technology, a small-scale printer, office equipment, computer, networking, power, security, and IT services business.

## Initial repository assessment

Before changing files:

1. Inspect the entire repository and identify:
   - Framework and programming languages
   - Frontend structure
   - Backend/API structure
   - Database and ORM
   - Authentication system
   - Existing product, order, cart, and user functionality
   - Available scripts, tests, linting, and build commands

2. Preserve functional backend services, authentication, database configuration, environment-variable handling, APIs, deployment files, and integrations unless they are unusable.

3. Replace the existing customer-facing and administrative interface.

4. Do not delete:
   - `.git`
   - `.env` or `.env.example`
   - Package lock files
   - Database migrations
   - Deployment configuration
   - Working APIs or integrations

5. Run the existing application before rebuilding it and record any pre-existing errors.

## Design direction

Create an Amazon-inspired e-commerce experience, but do not copy Amazon’s logo, branding, copyrighted assets, wording, source code, or exact visual design.

Use an original Ceter Technology identity with:

- A professional technology and office-equipment appearance
- Dense but organized product discovery
- Clear visual hierarchy
- Fast navigation
- Responsive layouts
- Accessible controls
- Original components and styling
- Consistent spacing, typography, buttons, forms, cards, and status indicators

The website must work well for both customers and administrators.

## Data and architecture

1. Use the existing technology stack unless a change is technically necessary.
2. Reuse working backend functionality.
3. Create reusable components rather than duplicating markup.
4. Model the category hierarchy properly instead of hardcoding every menu.
5. Add database migrations or seed scripts when required.
6. Create realistic demonstration products across major categories when the database is empty.
7. Clearly identify seeded demonstration data.
8. Do not expose secrets in frontend code.
9. Preserve environment-variable use.
10. Validate and sanitize submitted data.
11. Protect administrative routes.
12. Enforce role-based access where supported.
13. Handle API loading, empty, success, and error states.
